## Proposed schema, essential fields and constraints

Use consistent bigint PK/FK types, explicit nullable fields, named constraints, documented delete behavior and useful created/updated timestamps. Avoid giant unvalidated JSON as the entire database. JSON is suitable for immutable destination/display snapshots and bounded audit summaries; authorization and FKs remain relational.

### Scope and identity

- `barangays`: id, name, optional official address/municipality, map scope identifier. Seed fictional known locations only; unknown map artwork is unavailable.
- `households`: id, barangay_id FK, address, nullable map_x/map_y decimal percentages, revision. Paired coordinates0–100 inclusive; `(0,0)` valid, unknown stays null. These are not latitude/longitude.
- `users`: id, barangay_id FK, nullable household_id FK, full_name, normalized unique email, password hash, contact, account status, independent resident/Captain memberships, last_login_at. Operational role comes from current appointment; DTO retains existing role flags. No public route can assign Captain. Validate household/tenant consistency in services and, where practical, composite keys.
- `tanod_memberships`: unique user/barangay, pool identity/reference and active membership metadata. Personnel module cannot create/delete these members. Preserve membership when appointed or returned.
- `personnel_appointments`: one current record per user, barangay, role(Secretary/Responder/Rescuer or nullable unassigned), source(existing/external/appointed Tanod), status, effective date, assigning Captain FK, revision and required personnel details. Normalize private requirement documents separately.
- `personnel_history`: person/current-appointment reference, from_role/to_role, source/status as needed, effective date, actor FK, role-at-action snapshot, notes, recorded_at. No cascade deletion of service history.
- `capacity_guards`: unique `(scope_type,scope_id,kind)` rows for barangay staffing serialization and per-person dispatch/role-change synchronization. Define creation/lock protocol so simultaneous first use cannot create two guards; preseed/create with a unique upsert followed by lock.

### Verification and files

- `verifications`: resident_id, barangay_id, review_status, deadline_at, nullable current_submission_id, revision, reviewer_id/reviewed_at, correction reason/time. States Pending/Resubmission requested/Approved/Rejected/Expired. Prevent a second current active application for a resident using a guard/unique current pointer, while retaining historical applications.
- `verification_submissions`: application FK, submission revision, submitted_at; unique(application_id,revision). A decision must identify exact current submission.
- `documents`: private disk/object key, safe original name, detected MIME, bytes, uploader, scope, and explicit nullable submission/personnel owner FKs with exactly one valid owner. Storage bytes never in a public directory or database audit JSON. Stage/commit/cleanup coordinated with P1. Verification validID/proof max10MiB each JPEG/PNG/PDF; personnel max10 documents5MiB each. ## Business rules and transaction protocol

1. Current staffing limits are **Secretary3, Responder6, Rescuer6 occupied roles per barangay**. Inactive staff still occupying a position count. The brief says active Secretaries; document discrepancy and preserve current behavior unless the team explicitly changes it.
2. Normal concurrent incident capacity **Responder2/Rescuer1**. Current frontend has a confirmed/reasoned/audited Captain override; brief says no exceptions. Preserve metadata/design for that narrow exception, disabled for live use pending team ratification. Secretary never overrides. An override cannot bypass inactive account, tenant, role or workflow checks.
3. Captain-only external addition/appointment/reassignment/removal; immutable Tanod pool membership. Removing appointed Tanod returns them to pool; external person becomes unassigned, never physically deleted. Role change blocked by active old-role responsibility on an unresolved incident.
4. Manual acknowledgment includes selected responder. Rescue-required response never automatically selects a rescuer. Response/rescue completion releases capacity without auto-resolving incident; no-rescue resolution requires completed response and explicit false boolean. Policies/services are developer-owned, but database tests/fixtures must support them.
5. Verification corrections append to same application, reset Pending/new7-day deadline. Correction waiting does not expire. Rejected/Expired reapplication is new; Approved final. Review locks exact submission revision; no silently reviewing an older document.
6. Propose and get P1/P2 agreement on **one lock order**. Staffing changes acquire barangay staffing guard then per-person guard; dispatch acquires all affected per-person guards sorted by userID before incident/current assignment locks. Every participating path follows compatible ordering. Re-read active role/state/capacity/revision under locks. Avoid locking an incident first then waiting on a guard in a role-change path using reverse order.
7. Guard COUNT(active assignments) with a shared person lock across different incidents. A row lock on just the target incident is insufficient. Transfers lock both personnel; role changes share guard; inactive facility/new-rescue races use common row lock protocol. Reject stale revision409; retry internal deadlocks safely without duplicating external sends.
8. Domain state/history/audit/outbox commit together. External mail/SMS only after commit through queue. Provider idempotency is not assumed; accepted-but-timed-out sends may be uncertain. Database dedupe guarantees logical commands, not exactly-once network delivery.
