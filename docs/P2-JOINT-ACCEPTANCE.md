## Adopted explicit revision handoff

P1 a821d5d explicitly versioned its previously unimplemented contract to `IncidentPhotos::attach(EffectiveIdentity $observed, string $uploadId, int $incidentId, int $expectedRevision): int`. P2 accepts this fourth required argument and supersedes its earlier three-argument proposal. Pass the original opening revision; never infer it from storage. Both owners now adopt exact source rules and a guarded first-execution boundary, while byte/schema/consent implementations remain absent. No P1 source is changed by P2.

1. Capture P1's original EffectiveIdentity, the original submission key, exact canonical body (including future agreed upload references), incident ID and opening expected_revision. Validate input strictly. No backend photo fields are accepted until real services exist.
2. Enter the existing P2 `once` command boundary. Lock the original actor and validate the captured generation/current identity. Look up the actor/route/key command outcome and compare the **whole** original body hash.
3. On a matching previous success, authorize the original resource under current identity/source read rules and replay the persisted command result/current authorized projection. Do not call attach again, consume the staged token again, repeat audits/events, or rerun the stale original attachment revision as a new write. A different body conflicts. Revoked identity still denies a successful-command replay. A key is route/actor scoped; token-to-incident authority must still prevent cross-incident token reuse.
4. On a first execution only, declare all mutable people and the exact incident using the same GuardedStore/connection; current ordered person guards precede incident/assignments. Call the exact attach source policy with the original observed identity and original expected_revision **before mutating source revision**. The actor must remain approved reporter and the source Pending/Acknowledged.
5. P1's attach implementation then locks each actual upload metadata row after the incident boundary, checking its original owner/scope/generation, readiness, expiry, cleanup claim, immutable byte evidence and exact association. It must not acquire a new lower-ranked user/incident lock after a photo lock, fetch a new revision, accept a fabricated receipt, or assume a filename is a staged object. P1 should assert the caller's declared actor/incident guard scope before any token mutation. Agree multi-token lock ordering (stable metadata ID order) and token error mapping with DBA to avoid token-order inversions.
6. The original P2 source edit/revision, real metadata attachment, command outcome, and any applicable history/audit/outbox writes commit or roll back on the same connection. Attachment-only changes must receive the agreed source revision/audit treatment; no-op details semantics must not silently hide a new attachment. The existing plain-details behavior is unchanged in this phase.
7. Byte staging/inspection is a separate operation; no filesystem move/delete or network action happens in a retried source transaction. SOS remains immediate and does not wait for photo staging or SMS. Preserve the original two-step workflow and disabled controls while unavailable.

P2 adopts P1's four-argument source boundary; DBA also adopts the once-miss placement in its published metadata agreement. Actual-service proof is still required on steps 3-6. Calling source policy before *every* retry would incorrectly reject a successfully committed command after its revision advanced. Calling it after details mutation would compare the opening revision against the wrong version. Neither workaround may refresh the original revision or session identity.

## Download and cleanup boundary

P1 loads the real immutable attachment-to-incident association without holding a metadata mutation lock, then invokes `assertDownload` outside another transaction. P2 owns the short actor/incident current-read authorization transaction; owner/admin may read resolved history, operators require latest active exact-role assignment on an unresolved incident. P1 then validates/serves the actual immutable private object using its byte integrity/path/header policy. This is request-time authority; no midstream revocation promise is implied. A household reference policy or a client incident ID is insufficient.

Cleanup claims only expired unattached metadata and commits before byte deletion, with fenced outcome recording. If cleanup claims first, attachment fails and the whole source command rolls back; if attachment wins, cleanup must find the row ineligible. Metadata-first cleanup never subsequently waits on user/incident locks. These are required future races, not tested file behavior in this phase.
