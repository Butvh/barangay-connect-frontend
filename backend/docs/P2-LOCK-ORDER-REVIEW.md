## Confirmed defect

[RelationalStore::transaction](https://github.com/Butvh/barangay-connect-frontend/blob/3d23092883e0f24aa89b4c86ce93862e35880e3e/backend/app/Services/P2/Persistence/RelationalStore.php#L60) takes supplied operations-person/SOS guards, users/appointments, then incident/assignment and facility rows. That order is suitable **only if the supplied person set is complete** and nested work adds no earlier-rank locks.

[Module::atomic/once](https://github.com/Butvh/barangay-connect-frontend/blob/3d23092883e0f24aa89b4c86ce93862e35880e3e/backend/app/Services/P2/Module.php#L25) initially knows actor and selected candidates; once may open an actor-only outer transaction before nested work expands the set. [ReferenceData::user/person](https://github.com/Butvh/barangay-connect-frontend/blob/3d23092883e0f24aa89b4c86ce93862e35880e3e/backend/app/Services/P2/Persistence/ReferenceData.php#L77) converts any in-transaction person lookup into user/appointment/Tanod FOR UPDATE reads. Incident event/project code later looks up the resident, historical assigners and other participants. A person omitted from the original set can therefore be locked **after the incident**. Sorting each partial set does not establish a global order.

The actual acknowledgment trace records initial user locks for fictional Captain1047/Responder1048, incident19, then a newly locked resident1046. Re-locks of already protected users are excluded from the finding; scope bindings are not miscounted as user IDs. These IDs are disposable fixture identifiers, not production data. The important sequence is `users[actor,candidate] -> incident -> users[resident]`, not the numeric fixture values.

These tests now exist and were run; the earlier statement that P2 has no SQL adapter/race suite is superseded.

DBA adds the manual [p2-lock-order.php review gate](../tests/Review/p2-lock-order.php) and its worker. Both use the **actual unmodified P2 IncidentService, RelationalStore, references and typed writers**, with P2's published disposable test bindings. One actual acknowledgment supplies the lock trace. Two independent processes then start from a common barrier and call actual responder completion and actual resident detail editing on the same incident; no helper substitutes their domain writes.

Observed: both commands committed, exactly one response remained, victim_count=0, one row-lock wait, and a separate private MySQL observer measured zero added deadlocks during this run. **This is not a deadlock-free proof or correction acceptance.** The SQL order gate exits2 and reports `lock_order_accepted=false` because the late user is still present. Ordinary successful races and transaction retry cannot ratify an inverted lock plan. P2 still owns a deterministic failing concurrency regression and the actual correction.

The manual gate is intentionally outside default PHPUnit discovery; it is a separate unresolved cross-owner review gate, not an expected-success assertion disguised inside the green DBA suite. It requires APP_ENV=testing, DB_TEST_DISPOSABLE=1, exact DB_DATABASE=DB_TEST_DATABASE under `p2_test_*`, MySQL8.4/InnoDB and an already migrated disposable composition. It creates/retains only fictional review fixtures and sends nothing externally. It never targets a shared database.

## Precise P2 changes requested

1. Build one complete outermost lock plan: relevant staffing scope first, **all** affected operations-person IDs sorted, documented SOS/other kind guards, current user/appointment reads, incident IDs sorted, assignment IDs sorted, then facility rows. Include actor, resident/source owner, old/new transfer participants and any person whose current eligibility will be locked by the event/response projection. Do not fix this by adding an operations guard after the incident.
2. Where participants come from mutable history, take a nonauthoritative pre-read to form the plan, acquire all earlier-rank locks, then revalidate the exact current incident revision/assignment/participant set. A changed set must abort/restart the whole transaction before acquiring additional lower-rank locks. Preserve the caller's observed generation, submitted key/body and revision; do not silently refresh a stale command.
3. Make nested once/atomic work join a **subset of the outer plan**, or restart at the outermost boundary. It must not acquire a new lower-ID operations/user lock after another person/incident lock. Preserve caller commit ownership and full source/history/audit/outbox/idempotency rollback.
4. Separate current eligibility/authorization reads from minimal historical display-name projections. Do not apply `FOR UPDATE` to every person lookup merely because a transaction is open. Any mutation-authoritative person/source read must be current and protected by the plan; removing locks globally or using an old RR snapshot is not a correction. Review recipient and historical assignment/author lookups too.
5. Publish the failing regression, correction and exact tested commit. Retest actual response versus resident edit; competing assignment/transfer/completion/resolution; reversed actor/candidate ID orders; retained historical participants; same-incident/last-slot/stale-generation cases; and rollback/retry side effects.
