## P1 persistence/error and existing audit handoff

P1 owns the authenticated self-only GET/PUT. Absence returns not_granted/revision0 without inserting. New explicit grant/revoke starts revision1; conflicting concurrent creation hits SQLSTATE23000/1062, which P1 maps to stale revision409. Existing mutation uses exact tuple AND original revision in UPDATE, increments revision by exactly1, and requires rowCount1;0 means409. An arbitrary Eloquent touch/save without the next revision is rejected. P1 validates exact purpose/versions (422), original identity/generation (401), current grant role/scope (403) and unavailable persistence (503). SQL is defense in depth, not identity/consent authorization.

The update guard freezes id/user/scope/purpose/channel/recorded_by/created_at, requires exact next revision and monotonic updated_at, and preserves prior granted_at on revocation. Grant/revoke times must pair with state and fit creation/update chronology. Regrant is a new explicit grant/revision; do not renew consent from password or role changes. Eloquent deletion and any nonempty downgrade fail notification_preferences_retained. Empty down is reversible. Partial table-before-trigger failure repairs only a compatible missing trigger; incompatible table/trigger objects are retained and rejected.

Keep preference write and the EXISTING typed audit recorder in the same named connection transaction. The current v1 audit vocabulary supports resource user/<owner id>, action notification_preference.changed, summary status/revision plus reason as canonical server-generated bounded JSON containing preference_id,purpose,channel,from,to,policy_version,template_version. Actor/scope/role/time remain in existing audit columns. Do not put client prose, phone or message in reason, introduce a second audit writer, or silently expand P1's DTO vocabulary. Tests exercise the actual P2 TypedAuditRecorder and prove both source failure and audit failure roll back the preference.
